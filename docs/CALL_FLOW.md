# Call Flow

This document describes the production calling flow for the Spring Boot + Twilio + Firebase application.

## High-level architecture

```text
Browser / Mobile Browser
  |  Firebase or simple login
  |  /user/token
  v
Spring Boot API  <-------------------> Firebase Firestore
  |                                  app_config, users, wallet,
  |                                  twilio_numbers, call history
  |
  | Twilio Voice SDK access token
  v
Twilio Voice SDK in browser
  |
  | device.connect({ DialedNumber })
  v
Twilio TwiML App
  |
  | POST /call/voice
  v
Dynamic TwiML XML
  |
  | <Dial><Number>...</Number></Dial>
  v
Twilio PSTN
  |
  | status callbacks / dial completion
  v
Spring Boot API
```

## 1. Browser request

1. The user opens the public web page over HTTPS.
2. The browser initializes the Twilio Voice JavaScript SDK.
3. The user signs in with Google or the simple phone-number login flow.
4. The browser requests `/user/token`.
5. Spring Boot returns a Twilio Voice access token with:
   - `identity` from the user's Firestore `temp` field.
   - outgoing TwiML App SID from Firestore `app_config.twilio_app_sid`.
   - incoming calls allowed.
6. The browser registers `Twilio.Device`.
7. On desktop or mobile, the user enters a destination and taps Call.
8. Mobile browsers require microphone permission from a user gesture. `quickstart.js` pre-warms `getUserMedia` before asynchronous wallet/network calls so iOS/Android browsers keep the permission gesture context.

## 2. Backend processing before call setup

Before calling Twilio from the browser, the frontend checks:

1. Maintenance mode through `/api/config/maintenance-mode`.
2. Wallet eligibility through `/user/wallet`.
3. Twilio Device readiness.
4. Microphone permission availability.

If these pass, the browser calls:

```javascript
device.connect({ params: { DialedNumber: to } })
```

The `DialedNumber` value is sent by Twilio to the TwiML App webhook.

## 3. TwiML App webhook

The Twilio TwiML App must have Voice Request URL:

```text
POST https://YOUR_DOMAIN/call/voice
```

Twilio calls `/call/voice` with parameters including:

- `CallSid`
- `From` / `Caller`, usually `client:CLIENT_IDENTITY`
- `DialedNumber`

`CallController.handleClientVoice` then:

1. Optionally validates the `X-Twilio-Signature` header when `TWILIO_VALIDATE_SIGNATURE=true`.
2. Resolves the destination from `DialedNumber` and fallback Twilio parameter names.
3. Resolves the caller identity by removing the `client:` prefix.
4. Builds absolute callback URLs from `APP_PUBLIC_BASE_URL`:
   - `/call/status-callback`
   - `/call/dial-complete`
5. Calls `CallService.createVoiceResponse(...)`.
6. Returns `Content-Type: application/xml` with TwiML.

## 4. Firestore lookup and call authorization

`CallService.createVoiceResponse(...)` performs:

1. Maintenance-mode check from Firestore `app_config`.
2. Caller lookup by Twilio identity in Firestore users.
3. Blocked-user check.
4. Wallet eligibility check.
5. Dynamic call time-limit calculation using:
   - wallet balance,
   - `call_rate_per_minute`,
   - `billing_interval_seconds`,
   - `max_call_duration_seconds`,
   - `auto_disconnect_threshold`.
6. Concurrent-call limit check through active `twilio_numbers` allocations.
7. Caller-ID allocation:
   - Prefer an available active number in Firestore `twilio_numbers`.
   - Fall back to Firestore `app_config.twilio_caller_id` when no pool record exists.

The allocated number is bound to the Twilio `CallSid` so callbacks can release it later.

## 5. Dynamic TwiML generation

For a valid PSTN destination, the backend now generates TwiML using Twilio's Java SDK builders. The response is XML and Spring returns it as `application/xml`.

Example shape:

```xml
<Response>
  <Dial callerId="+14155552671"
        timeLimit="600"
        answerOnBridge="true"
        action="https://YOUR_DOMAIN/call/dial-complete"
        method="POST">
    <Number statusCallback="https://YOUR_DOMAIN/call/status-callback"
            statusCallbackMethod="POST"
            statusCallbackEvent="initiated ringing answered completed">+919876543210</Number>
  </Dial>
</Response>
```

Important behavior:

- XML is generated by the Twilio SDK, so text and attributes are escaped correctly.
- `answerOnBridge="true"` prevents the browser leg from being considered answered before the PSTN side answers, which improves mobile UX and billing accuracy.
- PSTN numbers are normalized to E.164 where possible. Invalid phone-like input is rejected with spoken TwiML instead of invalid `<Number>` TwiML.
- `<Number>` status callbacks give per-PSTN-leg updates.
- `<Dial action>` gives final Dial outcome and deterministic number release.

If no destination is provided, the endpoint returns a simple `<Say>` response instead of trying to dial.

## 6. PSTN dialing

Twilio receives the TwiML and dials the `<Number>` using the allocated caller ID.

Possible outcomes:

- `initiated`
- `ringing`
- `answered`
- `completed`
- `busy`
- `no-answer`
- `failed`
- `canceled`

Twilio sends callbacks to `/call/status-callback` and `/call/dial-complete`.

## 7. Callback handling

### `/call/status-callback`

Receives Twilio status events from the TwiML App and from `<Number statusCallback>`. The controller logs:

- `CallSid`
- `DialCallSid`
- status
- from/to
- duration

For terminal states, it releases the allocated Twilio number.

### `/call/dial-complete`

Receives the `<Dial action>` request after the Dial verb finishes. It logs the Dial outcome and releases the allocated number by parent `CallSid`. It returns an empty TwiML `<Response/>` to end the Twilio instruction chain cleanly.

### `/call/outbound/status/{publicId}`

Used only by server-initiated outbound REST calls. It updates the `outbound_calls` Firestore record and releases the tracked number on terminal states.

## 8. Call completion and billing

The browser receives Twilio Voice SDK call events:

- `ringing`
- `accept`
- `disconnect`
- `cancel`
- `reject`
- `error`

Billing starts on `accept`, not on `ringing`. When the call ends, the browser posts `/call/charge` with:

- destination
- call SID
- total duration
- connected duration
- status
- start/end timestamps

`CallService.chargeUser(...)` uses a Firestore transaction to:

1. Avoid duplicate charges by checking wallet transaction reference ID.
2. Calculate billed seconds using `billing_interval_seconds`.
3. Apply `minimum_call_charge`.
4. Debit the wallet.
5. Save wallet transaction history.
6. Save call history.

Unanswered calls have `connectedDurationSeconds = 0` and are not charged.

## 9. Server-initiated outbound REST flow

This is separate from browser-to-PSTN calling.

```text
Browser/API client
  |
  | POST /call/outbound { destination, message }
  v
Spring Boot
  | Firestore authorization + number allocation
  | Twilio REST API Call.creator(...)
  v
Twilio
  |
  | POST /call/outbound/twiml/{publicId}
  v
Dynamic TwiML <Say>
  |
  | POST /call/outbound/status/{publicId}
  v
Spring Boot updates outbound call record and releases number
```

This path calls a PSTN destination and plays a configured message. It does not replace the TwiML App `/call/voice` browser calling flow.

## 10. Incoming PSTN flow

Twilio inbound webhooks do not include the browser's HTTP session. Therefore inbound PSTN calls must route explicitly:

```text
Twilio Number
  |
  | POST /call/direct-client?client=client-abc12345
  v
Spring Boot
  |
  | <Dial><Client>client-abc12345</Client></Dial>
  v
Registered browser Twilio.Device
```

If the `client` query parameter is omitted, the backend uses Firestore `app_config.twilio_incoming_client_identity`.

## Root breakage found

The browser calling flow depends on the TwiML App Voice URL requesting `/call/voice` and receiving a `<Dial><Number>...</Number></Dial>` response. Dynamic outbound TwiML endpoints such as `/call/outbound/twiml/{publicId}` are for server-initiated REST calls and return message TwiML, not browser-to-PSTN dialing TwiML. Pointing the TwiML App or phone-number webhook at those endpoints breaks browser PSTN calls.

The implementation has been hardened so `/call/voice` now generates valid dynamic TwiML with explicit XML content type, callback URLs, PSTN validation, callback logging, and deterministic number cleanup.
